# Contributing

Thanks for helping! The audience is people who are *not* mechanical engineers, so every feature has
two halves: the engineering and the explanation. A PR that adds a check should also add the
plain-language verdict text and, where it helps, a picture.

## Layout

- `fcharness/` — the package. `job.py`, `materials.py`, `verdict.py`, `report.py` are pure Python;
  everything else runs inside FreeCAD's Python.
- `run.py` — entry point (`FCH_JOB=<job.yaml> freecadcmd run.py`).
- `examples/` — example models (generated by scripts, never hand-edited binaries) and job files.
- `docs/examples/` — committed example reports, regenerated with `FCH_OUT=docs/examples`.
- `tests/test_*.py` — pure-Python unit tests: `python3 tests/test_job.py`.
- `tests/fc_benchmarks.py` — analytical benchmarks through the full pipeline: `freecadcmd tests/fc_benchmarks.py`
  (look for `BENCH FAIL`).

## Rules of thumb

- **No silent assumptions.** If the harness has to guess, the validator emits a warning that ends up in the report.
- **Validate the answer, not just the input.** New solver features need a self-check (equilibrium,
  mass balance, symmetry, …) and an analytical benchmark.
- **Keep console output quiet.** FreeCAD, gmsh and CalculiX print progress bars to raw file descriptors;
  wrap noisy calls in `fcenv.QuietConsole(log_path)`.
- **Top-level scripts must not raise** — FreeCADCmd re-executes a script whose top level throws.
- Read `FemMesh.Nodes` once; every access rebuilds the whole dict.
- Small commits whose message explains *why*.

## Running in CI

FreeCAD's AppImage or snap provides everything; no pip installs are needed for the FreeCAD-side code.
